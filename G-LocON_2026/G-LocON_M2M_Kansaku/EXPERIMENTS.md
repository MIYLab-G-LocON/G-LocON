## 検証の全体像と現在地（2026/10/05 時点）

本研究の主張は「接続相手を，自車の周りの距離ではなく**進行先の交差点**で決めると，少ないサーバ負荷で，必要な相手と事前に安定してつながれる」こと。
これを4つの層で確かめる。主は A と C（通信面），D（交通面）は補助。

| 層 | 確かめること | 方法 | 使うもの | 状況 |
|---|---|---|---|---|
| A. 方式の比較 | 従来G-LocONより，誰とつなぐかの決め方が良いか | SUMO の同じ走行の上で両方式を計算 | `compare_schemes.py`，`eval_run.py`，`eval_report.py`（サーバ・実機は不要） | **主の比較は完了**（E14，60実行）。τ・ρ・δ の比較（`params`）が残り |
| B. 実装の動作 | 作ったサーバ・アプリが，車が多くても正しく動くか | 実サーバ＋仮想クライアント（PC内） | `start_servers.py`, `sim_bridge.py` | **ほぼ完了**（E0, E1, E3, E7） |
| C. 実機での実測 | 実際の無線・実際のスマホで動くか。通信の数字はどうか | スマホ3台＋実サーバ（＋仮想クライアント） | アプリ，`sim_bridge.py` | **途中**（実機どうしのすれ違い，実機1台＋仮想車両は確認済み。測定用のログが未実装） |
| D. 交通への効果 | 危険情報が届くことで，急ブレーキ・追突が減るか | SUMO の車を減速させて比べる | `sim_bridge.py --control`, `run_scenario.py` | **効果は示せていない**（E1〜E3）。補助の扱い |

### 正式評価（層 A）の計画（2026/10/05 案。教授に確認してから確定）

これまでは条件を1回ずつ試して指標と条件を探ってきた。ここからは指標と条件を固定し，乱数を変えて繰り返す。
手順は [SimBridge/EVALUATION.md](G-LocON_V2V_Server/SimBridge/EVALUATION.md)（自分のPCで実行 → 表 → グラフ）。

**指標**（定義は README 7.5）

| 分類 | 指標 | 列名 | 良い方向 |
|---|---|---|---|
| 負荷 | 制御メッセージ数（回/台・分） | `ctrl_per_veh_min` | 少ない |
| 負荷 | 同時につながる相手の数 | `peers_mean` | 少ない |
| 狙った交差点 | 判断の余裕を持って接続（エッジサーバ交差点） | `met_margin_es` | 高い |
| 無駄 | ルートが交わらない相手との接続 | `noshare_pct` | 低い |
| 安定 | 境目でのつなぎ直し（つなぎ直し A，回/台・分） | `reconn_A_per_veh_min` | 少ない |
| 安定 | 10秒以下で切れた接続 | `short_pct` | 低い |
| 参考 | すれ違い全体で接続，無駄な接続 | `enc_connected`，`wasted_pct` | 狙いの違いとして示す |

**条件**

| 計画 | 変えるもの | 固定するもの | 実行数 |
|---|---|---|---|
| `main`（主） | 地図（大学周辺，幹線道路を含む）× 交通量（少・中・多）× 測位誤差（なし，5m・ゆっくり変わる）× 乱数5回。方式（本システム，従来 100/150/200m）は1実行の中で同時に計算 | 本システム τ=15秒，ρ=100m，δ=100m | 60 |
| `params`（副） | 本システムの τ（15/30/45秒），ρ（0/50/100/150m），δ（30/60/100/150m）を1つずつ × 乱数5回 | 大学周辺，交通量 中，測位誤差5m | 5 |
| `noise`（補） | 測位誤差の大きさ（3m・5m）と変わり方（ゆっくり・ばらばら）× 地図2つ × 乱数3回 | 交通量 中 | 24 |

- 交通量（車の発生間隔）: 大学周辺 3.0 / 1.5 / 0.75秒，幹線道路を含む地図 1.5 / 0.9 / 0.6秒。
- 乱数: SUMO の乱数と，車の出発地・目的地の乱数を同時に変える。エッジサーバの位置は変えない。
- 外したもの: 1台の中での速度のゆらぎ（E13 で影響が見えなかった。入れ方が弱い可能性は残る），従来300m，エッジサーバの数・間隔（E6 で確認済み。配置は別の課題）。
- 本システムの ETA は，アプリと同じ直線距離÷速度で計算する（E13 までは道のりで計算していた。`--eta-by route` で再現できる）。

### 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| エッジサーバの置き方 | 交通量の多い交差点から置く（大学周辺20か所，幹線道路の地図40か所），互いに100m以上離す | どこに置くのが良いかは別の研究課題（今後のテーマ）とし，今は方式の挙動を確かめやすい理想的な配置を使う |
| 参加の条件 | ETA < τ，**または参加円（半径 ρ）の中**。既定 τ=15秒，ρ=100m | 渋滞でゆっくり進む車の参加が遅れるため（E5） |
| 離脱の条件 | 通過済み（20mまで近づいた）・δ 以上離れた・遠ざかっている。既定 δ=100m（以前は60m） | すれ違いは交差点を出た後にも起きる（E9） |
| 従来方式の条件 | 半径100m（元の既定）を基準に 100/150/200m，問い合わせ約2秒ごと | 元の G-LocON（`G-LocON_2024`）のプログラムの値に合わせる（E10） |
| 評価の軸 | すれ違い全部ではなく，狙った交差点で判断の余裕を持ってつながれているか，と負荷・無駄・安定 | 本システムは交通量・事故の多い交差点でだけつながる方式で，従来方式とは狙いが違う（E12） |
| 判断の余裕 | 4.1秒 + 速度 ÷ 2.0 m/s²（国土交通省のガイドラインの値を組み合わせた式） | E12 |
| つなぎ直しの分類 | A = 切れてから10秒以内に，2台の距離の変化が50m未満のままつながり直した。B = それ以外 | E12 |
| 測位誤差 | 接続の判断に使う位置に 5m の誤差を加えた条件を入れる | SUMO の位置は誤差ゼロで，従来方式の境目での出入りが起きないため（E13） |
| 地図 | 大学周辺（1.8×1.15km，生活道路中心）と，幹線道路を含む地図（3.0×2.7km）の2つ | 交通量・速度の高い道路でも確かめる（E11） |

「狙った交差点で判断の余裕を持ってつながれているか」「負荷」「無駄」「安定」で比べる（指標の定義は README 7.5）。

| 負荷 | 制御メッセージ/台・分 | 35 / 16 | 95 / 76 | 102 / 79 | 114 / 82 | **本システム** |

### わかっていること

- 判断の余裕（国土交通省のガイドラインの値から計算。時速40kmで約10秒）で数えると，本システムは従来方式のどの半径よりも良い。
  従来方式は，つながってはいるが判断に足る時間が残っていない組が多い。
- 制御メッセージは 1/3〜1/5。ルートが交わらない相手とはつながらない。
- つなぎ直し A（10秒以内に，位置関係がほぼ同じままつながり直す）は，位置に誤差がなければ本システムのほうが多い
  （並んで走る車どうしが，交差点のグループを抜けて次でまた一緒になるため）。
  **測位誤差（5m）を入れると逆転する**（E13）。従来方式は円の境目でばたつき，車が多いほど増える（幹線道路で 3〜10回/台・分）。
  本システムは誤差を入れても変わらない（離脱は「通過済み・δ以上・遠ざかっている」の3条件，通過後は同じ交差点に入り直さないため）。
- 1台の中での速度のゆらぎ（±10%）は，つなぎ直しにほとんど影響しない（E13）。
- 条件: δ=100m，τ=15秒が良い（E9）。ρ は混雑時に効く（E5）。エッジサーバは交通量の多い交差点に詰めて置く（E6）。
- 実装の動作: JOIN は全て返信あり，グループ一覧の一致率 100.0%，危険情報は実際の通信で 87% に届く（E7）。

### まだ言えないこと

- すべて1回の結果。乱数・交通流・交通量を変えた繰り返しはこれから。
- **E11 で，幹線道路を含む地図では本システムが拾えるすれ違いは 71% にとどまると分かった**（対向 66%，交差 82%）。上の表（大学周辺の地図）より不利。詳しくは E11。
- 今の地図は生活道路が中心（ほぼ片側1車線，信号12か所）。幹線道路・速い道路・信号での追いつきなど，従来方式でつなぎ直しが増えるはずの場面が少ない。
- 通信の遅れ（つながると決まってから実際に通信できるまで）は0秒として計算している。
- 安全面（急ブレーキ・追突）の改善は示せていない（E2, E3）。

1. 幹線道路を含む地図を追加する（地図データの取得が必要）
2. 条件を決めて，乱数・交通流・交通量を変えて複数回まわす

## E0. SUMO連携の動作確認（2026/09/29）

- **目的**: SUMO の車を仮想クライアントとして実サーバに参加させる仕組みと，アプリとの接続が動くか。
- **方法**: エッジサーバ10台・MasterServer を起動し，仮想クライアント（同時最大約50台）と模擬端末1台。旧シナリオ（1km四方）。
- **結果**: JOIN 152件すべてに返信（応答時間 中央値14ms，95% 26ms）。グループ一覧の一致率 100%（3,986回の比較で欠け・余分なし）。
  模擬端末はルート受信 → MasterServer問い合わせ → JOIN → メンバー一覧受信 → 仮想車両10台から位置を受信，到着で次の車へ乗り換え。
  アプリの SimBridgeClient（Java）も同じブリッジと通信できた（ルート・位置約370回・乗り換え3回）。
- **次に変えること**: 車両制御を入れる（E1）。

## E1. 車両制御の動作確認（2026/10/02）

- **目的**: 危険情報をグループ＋P2Pで届け，接近中の車だけ減速させる仕組みが動くか。
- **方法**: PC上でサーバ（Master 1・Edge 10）を起動し，全車両を仮想クライアントとして `sim_bridge.py --control system`。
  シナリオは 1km四方・エッジサーバ10か所（ランダム）・急停止40件（固定）。V2Vなし・理想V2Vと `summarize.py` で比較。
- **結果**: 急停止40件のうち35〜36件で送信（残りはグループ未参加），通知約130件，うち減速21〜24件，遅延 中央値10〜13ms。
  エリア全体の指標（ヒヤリハット約1360〜1380，急制動約330〜350）は3条件で差なし。
- **考察**: エリア全体の指標は，急停止と無関係な交差点での減速が大半で，通知の効果を表さない。
- **次に変えること**: 急停止した車に近づいた車だけを取り出して測る（E2）。

## E2. 急停止の通知の評価（2026/10/02）

- **目的**: 急停止した車に実際に近づいた車に，通知が届いているか。急ブレーキは減るか。
- **前との違い**: 近づいた車（後ろ150m以内）を SUMO の正解から拾う `followers.csv` を追加。急停止は後続車がいるときだけ起こす。
  減速のさせ方を修正（速度の上限を今の速度から 2 m/s² ずつ下げる。以前は通知を受けた車のほうが急ブレーキになっていた）。
- **方法**: E1 と同じ旧シナリオ。V2Vなし，理想 τ=15/30/45，本システム τ=15/30/45，各1回。

## E8. 検証方法の見直し: 方式に寄らない指標の追加（2026/10/04）

    （エッジサーバの無い場所でのすれ違い。同じ道の前後・対向を含む）。
  - つなぎ直しは本システムのほうが多い（18% 対 10〜12%）。交差点Aのグループを抜け，次の交差点Bで同じ相手とまた一緒になるため。予想と逆の結果。
  - 近づかないまま終わる接続は，従来は半径を広げるほど増える（25→54→67%）。本システムは 45%。
- **次に変えること**: どの指標を主にするかを決めてから，τ・ρ・δ・交通量を振って回す。つなぎ直しを減らす方法（次の交差点でも一緒になる相手は切らない）を検討。
